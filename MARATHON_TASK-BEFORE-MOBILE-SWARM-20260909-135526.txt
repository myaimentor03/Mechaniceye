P0 BETA DIRECTIVE - MOBILE MULTIMODAL EVIDENCE
Added September 7, 2026
============================================================

PUBLIC BETA IS NOT ACCEPTABLE AS A TEXT-ONLY VEHICLE SYMPTOM PRODUCT.

Drivable's core beta value proposition requires real evidence captured from the vehicle using the user's phone.

P0 BETA REQUIREMENT:
The end-to-end Drivable Check must support and verify:

1. Real phone vibration / motion sensor capture.
   - Do not ship simulated, random, placeholder, or fabricated vibration values.
   - Use actual supported mobile device sensor APIs.
   - Record enough metadata to distinguish genuine sensor capture from unavailable/unsupported capture.

2. Real vehicle audio capture.
   - Record actual vehicle/engine sound from the phone.
   - Upload and associate the audio with the correct diagnosis case.

3. Photo capture and upload.
   - Associate uploaded evidence with the correct case.
   - Preserve private-storage and access-control requirements.

4. Video capture and upload where technically supported for beta.
   - Associate video with the correct diagnosis case.

5. Evidence persistence.
   - Photo, audio, video, vibration/sensor evidence must remain linked to the proper intake/case.
   - Do not silently lose evidence.
   - Production storage must fail closed when required configuration is unavailable.

6. REAL ANALYSIS PIPELINE.
   - Capturing/uploading evidence alone does NOT satisfy this requirement.
   - Drivable must actually pass supported evidence into the diagnosis/analysis pipeline.
   - Results must accurately identify which evidence was analyzed.
   - Never claim an evidence type was analyzed when it was not.
   - Human-entered symptoms are supporting evidence, not a substitute for phone-captured evidence.

7. Vehicle context.
   - Combine captured evidence with available year/make/model/VIN/NHTSA/vehicle context where appropriate.

8. Mobile end-to-end acceptance.
   - Physical-device test must cover:
     phone -> capture -> upload -> persistence -> analysis -> result/report.
   - Test normal capture plus permission denial, unsupported sensor, upload failure, and unavailable-analysis cases.

9. Truthful degraded behavior.
   - If a device cannot provide a sensor/evidence type, say so clearly.
   - Never substitute fake sensor values.
   - Never present human-review-only media as AI-analyzed evidence.

BETA PRIORITY:
Until this pipeline works end-to-end, treat mobile multimodal evidence as a P0 launch gate.

Do not postpone real vibration/audio/photo evidence analysis to post-beta merely to publish sooner.
