# Make Email Testing Guide V1

## Purpose

This guide helps Glenn safely test Drivable admin notifications and customer confirmation emails in Make using inboxes he owns and controls.

Use it with:

- `MAKE_MASTER_INTAKE_TEST_PAYLOADS_V1.md`
- `MAKE_MASTER_INTAKE_ROUTER_FIELD_MAPPING_V1.md`

The goal is to prove each router branch, field mapping, subject line, and email body before any message can reach a real customer.

## Safe Testing Rule

During testing, every customer confirmation module should either be disabled or temporarily mapped to a Glenn-owned test inbox. Do not map customer confirmation to `sellerEmail`, `buyerEmail`, `customer.email`, or `email` until that route is proven.

Also follow these rules:

- Use only fake test payloads and Glenn-owned inboxes.
- Label test messages clearly with `TEST` in the subject.
- Test one router branch at a time.
- Keep old working scenarios active until the matching master-router branch is proven.
- Do not use production customer addresses as test data.
- Prefer creating a Gmail draft instead of sending when reviewing sensitive diagnosis, safety, title, buying, or selling content.
- Confirm the recipient field immediately before every test run.

## Admin Email Modules

Admin email modules notify Glenn or an approved internal inbox that a new intake needs attention.

During testing:

1. Set the `To` field to a reliable Glenn-owned test inbox.
2. Do not map the `To` field from incoming customer data.
3. Prefix the subject with `[TEST]`.
4. Include the exact `intakeType` in the subject.
5. Include enough identifying information to find the matching Make run and workbook row.
6. Keep raw secrets, webhook URLs, credentials, and private tokens out of the email.

Recommended test subject pattern:

```text
[TEST] Drivable {{intakeType}} - {{contact name or case/listing ID}}
```

Recommended admin email body:

- Intake type
- Submitted time
- Source
- Contact name, email, and phone
- Vehicle year, make, model, trim, and mileage when available
- Scenario and report type when available
- Customer message, symptoms, known issues, or buyer questions
- AI summary generated by the OpenAI module in the same route
- Related case or listing ID
- Workbook tab and status
- A clear statement that this is a test

## Customer Confirmation Modules

Customer confirmation modules acknowledge receipt. They must not send diagnostic certainty, promises, approvals, or sensitive internal notes.

During testing:

- Keep the module disabled unless its recipient is temporarily hard-coded to a Glenn-owned test inbox.
- Do not map the recipient to a payload email field yet.
- Prefix the subject with `[TEST]`.
- Use receipt language, not outcome language.
- Do not promise a response time unless operations can consistently meet it.
- Do not include internal notes, risk flags, reviewer comments, or unapproved AI output.
- For diagnosis and buyer decisions, use informational language based on information provided and recommend appropriate in-person inspection.

Recommended test subject pattern:

```text
[TEST] Drivable received your {{request type}}
```

## Using Glenn-Owned Test Inboxes

A Glenn-owned test inbox is an email account Glenn can open, monitor, and safely use for automation testing.

For each test:

1. Put the same Glenn-owned test address in the Make module's `To` field.
2. Use a different subject suffix for each route.
3. Run only the matching test payload.
4. Verify delivery, formatting, links, sender identity, and reply behavior.
5. Check spam and promotions folders.
6. Confirm no other recipient appears in `To`, `Cc`, or `Bcc`.
7. Record the successful Make run ID and test date.

Examples of useful subject suffixes:

- `CONCIERGE TEST`
- `SELLER TEST`
- `DIAGNOSIS TEST`
- `BUYER TEST`
- `INTERNAL REVIEW TEST`

## Do Not Use glennreckard@gmail.com If Full or Unreliable

Do not use `glennreckard@gmail.com` as the required test destination if the mailbox is full, delayed, inaccessible, filtering Make messages, or otherwise unreliable.

An unreliable inbox can make a working Make route look broken. Choose an inbox Glenn can confirm receives messages promptly and can be checked during every test.

## Temporary Admin Inbox Recommendation

Create or use one reliable temporary inbox dedicated to automation testing. It should:

- Be owned and accessible by Glenn.
- Have available storage.
- Allow messages from the connected Make email provider.
- Be checked for spam filtering.
- Receive both admin and temporarily redirected customer test messages.
- Never be populated with real customer data during test runs.

A simple temporary naming pattern is:

```text
drivable.automation.test@provider.example
```

This is a naming example only. Use a real inbox Glenn owns, not the example address.

## Future Domain Emails

When the Drivable domain and mail service are ready, separate operational roles:

- `support@domain` - Customer help and concierge replies
- `intake@domain` - Intake notifications and routing
- `listings@domain` - Seller and marketplace listing communication
- `reviews@domain` - Diagnosis and human-review communication
- `glenn@domain` - Glenn's direct internal/admin mailbox

Before enabling these addresses:

- Replace `domain` with the verified production domain.
- Confirm each mailbox or alias exists.
- Confirm sending-domain authentication is configured.
- Test delivery and replies.
- Decide which addresses are monitored by a person.
- Avoid using an unmonitored sender for messages that invite replies.

## How to Test Each Route

### support-concierge-request

Use the `support-concierge-request` payload from `MAKE_MASTER_INTAKE_TEST_PAYLOADS_V1.md`.

Admin email:

- Send only to Glenn's test inbox.
- Suggested subject: `[TEST] Drivable support-concierge-request - {{customerName}}`
- Include `intakeType`, contact fields, `topic`, `urgency`, `scenario`, `reportType`, message, related IDs, and the same-route AI summary.

Customer confirmation:

- Keep disabled or redirect to Glenn's test inbox.
- Confirm it acknowledges receipt without promising a diagnosis or response time.
- Do not expose admin notes or internal routing details.

Verify the `support-concierge-request` router branch fired and no sibling branch sent an email.

### marketplace-seller

Use the `marketplace-seller` test payload.

Admin email:

- Send only to Glenn's test inbox.
- Suggested subject: `[TEST] Drivable marketplace-seller - {{vehicleYear}} {{make}} {{model}}`
- Include seller contact, vehicle, mileage, asking price, title status, runs-and-drives status, listing type, known issues, recent repairs, and the same-route AI summary.

Customer confirmation:

- Keep disabled or redirect to Glenn's test inbox.
- Do not map `To` to `sellerEmail` until the route is proven.
- State only that the listing request was received for review.
- Do not promise publication, acceptance, sale, price, buyer interest, or payment outcome.

### diagnosis

Use the `diagnosis` test payload.

Admin email:

- Send only to Glenn's test inbox.
- Suggested subject: `[TEST] Drivable diagnosis - {{vehicle.year}} {{vehicle.make}} {{vehicle.model}}`
- Include contact, vehicle, symptoms, timing, media availability, scenario, report type, and the same-route confidence-rated AI summary.

Customer confirmation:

- Prefer a draft or keep disabled until diagnosis wording is reviewed.
- If testing delivery, redirect it to Glenn's test inbox.
- Do not map `To` to `customer.email` until the route is proven.
- Do not state that a cause is confirmed, that a repair is guaranteed, or that an in-person inspection is unnecessary.
- Include safety escalation language when appropriate.

### buyer-interest

Use the `buyer-interest` test payload.

Admin email:

- Send only to Glenn's test inbox.
- Suggested subject: `[TEST] Drivable buyer-interest - {{listingId}}`
- Include buyer contact, listing ID, vehicle, buyer questions, scenario, report type, and the same-route AI buyer summary.

Customer confirmation:

- Keep disabled or redirect to Glenn's test inbox.
- Do not map `To` to `buyerEmail`, `customer.email`, or another incoming buyer address until proven.
- State only that the interest or questions were received.
- Do not promise seller response, vehicle availability, title condition, inspection access, or transaction outcome.

Note: the test router contract uses `buyer-interest`. The current application may emit `marketplace-buyer-interest`. Confirm the actual filter contract before production email is enabled.

### internal-diagnosis-response

Use the `internal-diagnosis-response` test payload.

Admin email or draft:

- Send or create a draft only in Glenn's test inbox.
- Suggested subject: `[TEST] Drivable internal-diagnosis-response - {{caseId}}`
- Include case ID, reviewer, confidence level and reason, recommendation, decision paths, customer-ready summary, and safe internal notes.
- Confirm the summary or draft comes from the OpenAI module in this same route.

Customer confirmation:

- Keep disabled.
- This route should support internal review before customer delivery.
- Do not send `internalNotes`, unapproved recommendations, or raw OpenAI output to a customer.
- Enable a separate approved customer response step only after human review and route validation.

## What to Verify

For every route, verify:

- The admin email was received.
- The customer email was received only at Glenn's test inbox, if the customer module was enabled for testing.
- The subject line identifies the route.
- The body includes `intakeType`, contact, vehicle, scenario/reportType, and AI summary when those fields apply.
- No real customer received test mail.
- The sender and reply-to addresses are intentional.
- `To`, `Cc`, and `Bcc` contain only approved test recipients.
- The AI summary came from the OpenAI module in the same router branch.
- The message contains no credentials, webhook URLs, or internal secrets.
- The correct Make route fired exactly once.
- The matching workbook row and status were created as expected.

## When to Enable Real Customer Emails

Enable a route's real customer recipient mapping only after all of these are true:

1. The exact `intakeType` filter has been proven with a test payload.
2. The route writes the correct workbook row.
3. The admin email reaches the correct monitored inbox.
4. The customer template has been reviewed for tone, legal safety, and accuracy.
5. All test runs reached only Glenn-owned inboxes.
6. The recipient mapping has been inspected and deliberately changed to the correct customer field.
7. Missing or malformed email addresses are handled safely.
8. Duplicate runs do not send duplicate customer messages.
9. Error handling does not accidentally send a success confirmation.
10. The old scenario remains available until the replacement route works in production.

When enabling a real recipient, change only one route at a time and immediately run a controlled end-to-end test using an address Glenn owns.

## When to Keep Customer Emails Disabled

Keep customer email disabled when:

- The router branch has not completed its test checklist.
- The recipient field is uncertain.
- A Glenn-owned test inbox is not available.
- The source mailbox or sending domain is unreliable.
- The email contains unreviewed AI output.
- The route handles safety, title, structural, legal, payment, or high-cost repair decisions without human review.
- The route could expose internal notes or another customer's information.
- Duplicate prevention has not been tested.
- The old and new scenarios might both send a confirmation.
- The Make run, workbook write, or admin notification is failing.
- The customer template promises an outcome the service cannot guarantee.

When in doubt, keep the customer module disabled and prove the admin flow first.
